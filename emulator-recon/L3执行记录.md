## 0. 结论先行（先看这里）

1. **要求的伪装层已在实例 0 落地并跨重启生效**：雷电内置机型/IMEI/IMSI/SIM/AndroidID/MAC、build.prop（system/vendor/system_ext）、`ldspoof` 开机自愈、`/proc/cpuinfo` ARM64 伪装、root 痕迹清理、qemu 特征文件清理。逐项回显见 §3、§4，证据文件见 `emulator-recon/evidence/`。
2. **唯一验收项（99账号中心正常进入、无模拟器/虚拟机提示）未达成**：应用启动后在 **Splash / 登录页阶段必现 SIGSEGV**，崩溃点固定在 `libaqcenter.so` 的 `_Unwind_Resume(NULL)`（`x19=0` → 读 `0x10`），宿主侧帧全部在 `/system/vendor/lib64/libhoudini.so`。该崩溃在「root 开/关、ABI 改 arm64、清数据、以及本轮全量伪装 + 去 root + 假 ARM cpuinfo」后都复现，与 L2 记录一致。
3. 根因是 **Houdini 在 x86_64 上转译执行 ARM64 C++ 异常展开**，不是属性/root/应用列表这类 L3 用户态检测层能修的问题；要在雷电内放行，只能走 L4（换 native bridge / 原生补丁 / Frida 定位），或换 ARM64 真机/云真机。该判断与 `L3方案.md` §0 一致，本轮用实例 0 的实机证据再次确认。
4. **本轮新增一条对后续有用的能力**：LDPlayer 14 的「磁盘 → 系统盘设置 → 共享只读（取消勾选）」= `basicSettings.standaloneSysVmdk=true` 会为实例生成**独立的 `vms\<实例>\system.vdi`（实测 1,957,691,392 B）**，客户机内 `mount -o rw,remount /` 返回 0、`/system` 可写。这样可以在**单实例内**持久改 `/system`（build.prop、开机脚本、删特征文件），不再必须离线改共享 `system.vdi`。这一条是 L1/L2 记录里「/system 只读、只能离线改盘」的补充，不是推翻（离线改盘仍是共享只读模式下的做法）。

## 5. 为什么「全设备伪装」仍不够

- 崩溃发生在 ARM64 `libaqcenter.so` 的 C++ 异常展开路径，宿主帧全在 Houdini；这属于转译层的异常展开实现，不是 Java/属性/root/应用列表可改的检测面。
- 本轮已把用户态可改的信号改到极限：机型/指纹/system_ext 全一致、无 su、无 qemu 节点、`/proc/cpuinfo` 假 ARM64、root 通道改走 `adb root`；崩溃仍 100% 复现。
- L2 另行排除：root 开/关、ABI 改 arm64、清数据/重装——均不影响崩溃。
- 与 `L3方案.md` §0 的判断一致：现有证据下，能直接绕开 Houdini 的是 ARM64 真机/云真机；留在雷电则属于 L4（换 libndk/新版 Houdini、或对 `libaqcenter.so`/`AntiDebug::*` 做原生补丁/Frida 定位）。
