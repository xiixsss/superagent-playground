## 0. 先给结论（现有证据下能落地的那一条）

**一句话：在 LDPlayer 14（x86_64 + Houdini）里，L3 的「伪装真机/过检测」教程解决不了当前阻断点；现有证据下能直接落地的是 ARM64 环境（ARM64 真机或 ARM64 云真机）。**

依据不是猜测，而是 L2 的实测崩溃链：

1. 应用能过隐私协议、进入登录页 `com.nd.aqcenter/.login.LoginActivity`；
2. 登录页显示后 1–7 秒内必现 `SIGSEGV`；
3. ARM 侧崩在 `libaqcenter.so` 的 `_Unwind_Resume(NULL)`（`x19=0`，随后 `ldr x3,[x19,#0x10]` 读 `0x10`）；
4. 宿主侧 4 帧全部落在 `/system/vendor/lib64/libhoudini.so`（fault addr `0x10`，null deref）。

这属于 **Houdini 在 x86_64 上转译执行 C++ 异常展开时的行为**，不是「build.prop 没改干净」「root 没藏好」「应用列表没藏」这类 L3 检测层问题。L2 已逐项排除：

| 变量 | L2 实测结果 |
|---|---|
| root 开 / 关 | 关 root、`/system/xbin/su` 不存在时，登录页仍崩 |
| `ro.product.cpu.abi*` 改 arm64-v8a | `getprop` 已生效，仍崩 |
| 清数据 / 重装 | `pm clear` 只解决 WCDB「初始化失败」，登录页仍崩 |
| 模拟器检测点 | 静态确认有 qemu/vbox/nox/mumu//proc/root/magisk/AntiDebug 等，但用户态无法抹掉 `/proc/cpuinfo`、qemu 设备节点、Houdini 映射本身 |

因此本方案的排序是：

- **P0（能落地）**：ARM64 真机 / ARM64 云真机，绕开 Houdini。步骤见 §3.1。
- **P1（雷电内能做的全部 L3）**：Kitsune Mask + Zygisk Next + LSPosed/Vector + HMA 的检测层伪装。它能消掉 root/应用列表/部分属性信号，但**不能消掉 native `AntiDebug::vir_check` 看到的 x86_64/Houdini//proc 特征，也不能修 `_Unwind_Resume` 崩溃**。单独做完 P1，99 仍然会崩；不要把 P1 当交付结果。
- **P2（雷电内的 L4 前置实验）**：换翻译层（libndk / 新版 Houdini）或 Frida/原生 hook。属于实验路径，未验证，风险高。
- **不采用**：只改机型/只删 qemu 文件、旧版「应用变量」、来路不明的「一键过检测」脚本/修改版 APK。

决策顺序（按投入产出）：

1. 能借到 **ARM64 真机** → 直接做 §3.1-A，约 30 分钟可判定 99 是否可用；这是最高优先级。
2. 没有真机 → 租 **ARM64 云真机**（先装 CPU-Z/DevCheck 验 `arm64-v8a`）→ §3.1-B。
3. 必须留在 LDPlayer → **不要重复 P1 的检测层伪装**（它不修崩溃）；直接开 L4，按 §3.3-C1/C2 在关闭其它实例、备份 `system.vdi` 后换翻译层，或 §3.3-C3 做 Frida 定位。

> 验收口径说明：如果「让 99 在雷电模拟器内正常使用」是硬指标，那么本工单的诚实结论是 **L3 用户态伪装做不到**；需要另开 L4（运行时补丁/换 native bridge/宿主层）工单。若允许「同一台 Windows 上换 ARM64 运行环境」，P0 就是可执行且可验收的路径。

**结论**：APK 只有 `arm64-v8a` 与 `armeabi-v7a` 两套 native 库。把 `ro.product.cpu.abi` 改成 `x86_64` 不会让应用原生运行，只会让它找不到可用的 native 库；改 `arm64-v8a` 也不会改变 native bridge —— LDPlayer 的 `ro.dalvik.vm.native.bridge` 仍是 `libhoudini.so`，L2 实测仍崩。NIS 壳的真实 `libaqcenter.so`（16,687,296 B）是运行时解密到 `/data/data/com.nd.aqcenter/files/templib/` 的，静态改 APK 里的 568 B stub 没有意义。

### 1.3 L2 崩溃证据（原文摘要）

L2 记录里的 logcat / dropbox 原文：

```
11-03 16:47:59.953 2331 2472 F libc : Fatal signal 11 (SIGSEGV), code 1 (SEGV_MAPERR),
fault addr 0x10 in tid 2472 (Thread-9), pid 2331 (com.nd.aqcenter)

arm backtrace: pc = 0000400021c94660, lr = 0000400021c9465c
  #00  pc 0000000000e9465c  /data/data/com.nd.aqcenter/files/templib/libaqcenter.so
  r00(r19)=0x0000000000000000

0x00e94650  mov x19, x0
0x00e94654  ldp x29, x30, [sp], #0x10
0x00e94658  bl 0xe9818c            ; _Unwind_Resume 辅助
0x00e9465c  ldr x3, [x19, #0x10]   ; x19=0 → 读 0x10 → SEGV_MAPERR
```

宿主侧：

```
signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x0000000000000010
Cause: null pointer dereference
4 total frames
backtrace:
  #00 pc 00000000001053af  /system/vendor/lib64/libhoudini.so
  #01 pc 00000000001caa3b  /system/vendor/lib64/libhoudini.so
  #02 pc 00000000000e6bdf  /system/vendor/lib64/libhoudini.so
  #03 pc 000000000030e5e0  /system/vendor/lib64/libhoudini.so
```

**解读边界**：这说明「Houdini 的异常展开路径坏了」，不直接等价于「NIS 一定是在检测到模拟器后才抛异常」。两种可能都存在：

1. NIS 在登录阶段做原生环境检查，命中 x86_64/Houdini 后抛 C++ 异常，Houdini 展开时崩；
2. NIS 在该阶段正常抛异常（业务/完整性），Houdini 展开时崩。

无论哪一种，**用户态改属性/藏 root/藏应用列表都不能修 Houdini 的 `_Unwind_Resume` 实现**；要放行，必须让异常不发生（native 检测全过）或让异常不崩（换翻译层/打补丁）。

另一个已核实事实：L2 在 aqcenter 与 myht 的全部本地 dex / `resources.arsc` / so 中都没有「环境违法」四字；aqcenter 是 NIS 壳（`com.netease.nis.wrapper.*`），真实 dex 运行时解密。因此「环境违法」要么由服务端下发，要么在解密后的 dex 里，**不要从「改本地文案/找本地字符串」入手**；本机在等价阶段直接崩溃，弹窗根本没有机会出现。

### 2.1 常见教程/说法逐条判定

| 网上常见说法 | 对 99 的判定 | 依据 |
|---|---|---|
| 「改 build.prop 机型 + 删 qemu/goldfish 文件就能过检测」 | **不够**。L2 已改过机型/指纹、关过 root、改过 ABI；登录页仍崩。qemu 设备节点、`/proc/cpuinfo`、`libhoudini` 映射不是删几个文件能消掉的 | L2 §3/§4 |
| 「装 Magisk + LSPosed + HMA 就能过所有检测」 | **只对 Java/包枚举/root 痕迹类检测有效**；对 `libaqcenter.so` 的 native `AntiDebug` 无效，对 Houdini 崩溃无效 | §1.4、§3.2 |
| 「用应用变量改机型」 | **没有 Android 14 支持证据**（模块 2017/2019 停更）；即使能用也只改 Java 字段 | §2 X-1 |
| 「Frida 一键过检测脚本」 | **不作为放行**。目标有 `hook_by_tools`/`be_debug`/`lldb_check`；同厂商 `com.nd.myht` 历史实测 attach 即死；本目标未测 | §1.4、§3.3-C3 |

| 「用修改版 99 APK 去检测」 | **不采用**：破坏 NIS 签名/完整性，来源不可信，可能带后门或触发服务端风控 | — |

## 3. 可执行清单

### 3.1 P0：ARM64 真机 / ARM64 云真机（现有证据下能落地的路径）

#### A. ARM64 真机（推荐：干净 stock 机，不 root）

**准备**

1. 一台 Android 14+ 的 ARM64 手机（主流骁龙/天玑/麒麟均可），**不要 root、不要解 BL、不要装 LSPosed/Xposed**。
2. 关闭开发者选项里的「USB 调试」、mock location、VPN/代理、双开/分身、云手机/远程控制类 App（这些都可能被 `AntiDebug`/服务端计入环境分）。
3. 安装 `com.nd.aqcenter` v1.6.23（小米应用商店页面可核：[app.mi.com/details?id=com.nd.aqcenter](https://app.mi.com/details?id=com.nd.aqcenter)），或直接安装本机拉取的 APK（SHA256 见 §1.2）。

**验证设备真的是 ARM64、且没有 Houdini**

> `adb` 用 platform-tools（本机也可用 `D:\leidian\LDPlayer14\adb.exe`）。下面的检查/安装完成后，**关闭 USB 调试并拔线**，再打开 99 复测，避免开发者选项本身被计入环境。

```powershell
adb shell getprop ro.product.cpu.abi            # 期望 arm64-v8a
adb shell getprop ro.build.version.sdk          # 期望 >= 34
adb shell getprop ro.kernel.qemu                # 期望空
adb shell getprop ro.debuggable                 # 期望 0（user 版）
adb shell getprop ro.secure                     # 期望 1
adb shell "ls /system/lib64/libhoudini.so"      # 期望 No such file or directory
```

**安装与观察**

```powershell
$apk = '.\runs\l3\aqcenter-base.apk'   # 本机拉取的 1.6.23；或直接从应用商店安装
adb install -r $apk
adb shell pm clear com.nd.aqcenter
adb shell am start -n com.nd.aqcenter/.splash.SplashActivity
# 同意隐私协议，停在登录页至少 60 秒，观察是否闪退/弹「环境违法」
adb logcat -b crash -d | Select-String "com.nd.aqcenter|_Unwind_Resume|libhoudini|SIGSEGV"
```

**通过标准**

- 登录页停留 > 60 秒，`logcat -b crash` 无 `com.nd.aqcenter` 的 `SIGSEGV`；
- 能完成账号登录，进入账号安全功能页；
- 不出现「环境违法 / 模拟器 / 多开」提示。

**如果真机仍报「环境违法」**

说明阻断在服务端/账号侧或其它环境信号，不在 Houdini：

1. 换一台完全干净的 stock 机（无 root、无框架、无多开、无 VPN、无 mock 定位）复测；
2. 用同一账号在一台已知正常的手机上登录，排除账号风控；
3. 若干净真机仍报，按服务端风控处理（换网络/换账号/联系客服），不要继续在模拟器里加模块。

#### B. ARM64 云真机（没有实体机时的替代）

1. 选厂商：雷电云手机（同厂，FAQ 明确有 Android 14）或红手指等；**必须选 Android 14 实例**。
2. **先验 ABI**：云机内安装 CPU-Z / DevCheck / Device Info HW，看 `ABI`/`Instruction Sets` 是否为 `arm64-v8a`；或看 `Build.SUPPORTED_ABIS` 第一项。若显示 `x86_64`/`x86`，立即换实例——那是 x86 云机，等于回到本文的 Houdini 问题。
3. 安装 APK（云机内浏览器/应用市场，或厂商的文件上传）；
4. 按 §3.1-A 的「通过标准」观察登录页与登录流程。

**适用性**：仅 ARM64 云机；x86 云机不适用。云手机可能被 99 判定为「虚拟化/云机」，若报「环境违法」，按 A 的排除法换实体机。

#### C. 本地纯 ARM 全系统模拟（可选，不推荐）

如果既没有真机也不想租云机，可在 Linux 宿主上用 Cuttlefish aarch64 + QEMU TCG 跑纯 ARM64 Android 14（无 Houdini）。代价：需要 Linux、几十 GB 磁盘、启动慢、GPU/传感器不完整。本机是 Windows + LDPlayer，**未执行**；仅作为「没有 ARM64 硬件时的最后手段」。参考：[XDA 帖](https://xdaforums.com/t/cuttlefish-aarch64-builds-on-amd64-x86_x64-host-using-qemu-tcg-translation.4783785/)（正文 403，未能核步骤）。

### 3.2 P1：LDPlayer 14 内的检测层（Kitsune → Zygisk Next → LSPosed/Vector → HMA）

> 这一节是「雷电内能做的全部 L3」。**做完它，99 的 `_Unwind_Resume` 崩溃仍然存在**；它的价值是消掉 root/应用列表/部分属性信号，为 L4 或服务端复测做准备。  
> 所有步骤都会改 `/system` 或装模块；执行前先做 §5 的备份。下文以 `--index 1`（adb `emulator-5556`）为例；用复制实例时换成对应索引/端口，但注意 `/system` 仍是共享的。

#### 0. 先决条件与备份

1. LDPlayer 14.0.29.0，实例已关闭（`ldconsole quit --index 1`）。
2. **复制实例不能隔离 `/system`**：LDPlayer 14 的 `system.vdi` 在安装根目录共享（`vms\leidianN\` 里只有 `data.vdi`/`sdcard.vdi`）；`ldconsole copy` 只隔离 data/sdcard。Kitsune 改 `/system` 会影响所有实例，所以**必须备份根目录 `system.vdi`，实验期间关闭其它实例**。若仍想降低影响，可复制实例后只在副本上装 App/测试，但不要在副本上装 Kitsune 就以为主实例安全。
3. 备份系统盘（必须，Kitsune 是「直接修改 /system」）：

```powershell
$ts = Get-Date -Format 'yyyyMMdd_HHmmss'
Copy-Item 'D:\leidian\LDPlayer14\system.vdi' "D:\leidian\LDPlayer14\system.vdi.bak_l3_$ts"
```

4. 记录当前属性（回滚用）：

```powershell
New-Item -ItemType Directory -Force runs | Out-Null
& 'D:\leidian\LDPlayer14\adb.exe' shell getprop > runs\l3_props_before.txt
```

#### 1. 打开 LDPlayer 的必要开关

- 设置 → 开启 **ROOT 权限**；
- 设置 → 磁盘 → **system 分区可写入**（不同版本叫「系统盘可写入」）；
- 保存 → 重启实例。

#### 2. 安装 Kitsune Mask（狐狸面具）27.2

- 版本：**Kitsune Mask 27.2**（教程声称：LDPlayer 14 仅支持该版本，不推荐官方 Magisk）。
- 来源：52pojie 教程附件/网盘（[帖内链接](https://www.52pojie.cn/thread-2113682-1-1.html) 给出 `https://wwbja.lanzouq.com/ic7Ga3snf35i`，提取码 `52pj`）；HuskyDG 的原仓库在 2026-11-03 查询已 404，官方 Releases 不可用，注意校验文件来源。
- 步骤（按教程）：
  1. 把 Kitsune Mask 27.2 APK 拖进模拟器安装；
  2. 打开面具 → 顶部「安装」→ **直接安装（直接修改 /system）** → 开始；
  3. 底部出现 `All done!` 后，**手动点右上角 X 关闭模拟器再启动**（模拟器自带重启按钮无效）；
  4. 用 MT 管理器（root 模式）删除 `/system/xbin/su`；首次失败可再删一次，提示「文件不存在」即完成。
- 作用：接管 root、提供 DenyList/模块管理；**不改变 Houdini**。

#### 3. 安装 Zygisk Next（1.4.2，教程实测；或最新 1.5.2）

- 文件：`Zygisk-Next-1.4.2.zip`（教程随包；最新为 [v1.5.2](https://github.com/Dr-TSNG/ZygiskNext/releases/tag/v1.5.2)）。
- 步骤：
  1. 把 zip 拖进模拟器（自动进 `Pictures` 共享目录）；
  2. 打开 Kitsune Mask → 模块 → 从本地安装 → 选该 zip；
  3. 重启模拟器。
- 配置（教程用 KsuWebUI）：
  - 安装 [KsuWebUI v1.0-34](https://github.com/5ec1cff/KsuWebUIStandalone/releases/tag/v1.0)，授予 root；
  - Zygisk Next 设置：**匿名内存（全内存运行）→ 开**；**Zygisk 链接器 → 开**；**排除策略 → 强制模式**（银行/金融类 App 场景）。
  - 若提示 `Please disable built-in zygisk of magisk`：在 Kitsune 设置里把 Magisk 自带的 Zygisk 相关选项全部取消，重启；仍不行就「全选→重启→全不选→重启」。
- 作用：Zygisk 实现 + root 隐藏增强；**不隐藏 `libhoudini.so` 映射、不隐藏 `/proc/cpuinfo`**。

#### 4. 安装 LSPosed / Vector

- 教程随包：`LSPosed-v2.1.0-7769-release.zip`（无法从 LSPosed GitHub Releases 复核该 tag；**不要把它当成可复现的官方版本**；优先用下面两个可核版本）。
- 可替代（更可核）：
  - [LSPosed v1.9.2](https://github.com/LSPosed/LSPosed/releases/tag/v1.9.2)（2023-10-11，release notes 明确「Fix hook crash on Android 14」）；
  - [Vector v2.2](https://github.com/JingMatrix/Vector/releases/tag/v2.2)（2026-08-04，LSPosed 维护分支，声称 Android 8.1–17）。
- 步骤：
  1. Kitsune 模块 → 从本地安装 LSPosed/Vector zip → 重启；
  2. 若面具里显示「Zygisk 未启用，此模块暂停加载」：从 zip 里解出 `manager.apk` 安装，打开管理器即可配置（教程称这是面具显示错误，不影响模块）；
  3. 确认 Zygisk 已启用、LSPosed/Vector 管理器能打开。
- 风险：`libaqcenter.so` 有 `AntiDebug::hook_by_tools`，**装框架本身可能增加被检测概率**；这一步不是「越装越安全」。

#### 5. 安装 HMA（Hide My Applist）3.8.3

- 来源：[HMA v3.8.3](https://github.com/Dr-TSNG/Hide-My-Applist/releases/tag/v3.8.3)（APK；release note 要求框架实现「允许在系统服务中加载原生库」，若 LSPosed 1.9.2 下不生效，改用 Vector 2.2 或回退旧版 HMA 自测）。
- 配置（参考 [LRFP HMA 指南](https://github.com/LRFP-Team/LRFP/blob/main/Bypassers/HMA.md)）：
  1. 安装 HMA APK；在 LSPosed/Vector 里启用 HMA，**作用域只勾「系统框架」**；
  2. 重启；
  3. HMA → 模板管理 → 新建**黑名单模板**，加入：Magisk/Kitsune、LSPosed/Vector、HMA 自身、ApplistDetector、以及任何多开/检测器/改机工具；
  4. HMA → 应用管理 → `com.nd.aqcenter` → 启用隐藏 → 选黑名单模板；
  5. 重启或强行停止 99 后重开。
- 作用：让 99 枚举不到这些包；**不影响 native `vir_check` 读 `/proc`、`/dev/qemu_pipe`、`ro.dalvik.vm.native.bridge`**。

#### 6. 自检（先证明「检测层确实生效」，再谈 99）

安装 [ApplistDetector V2.4](https://github.com/Dr-TSNG/ApplistDetector/releases/tag/V2.4)，分别记录：

- 装 HMA 前：能看到哪些 Magisk/LSPosed/多开包；
- 装 HMA 后：`com.nd.aqcenter` 作用域下应看不到黑名单里的包；
- 用 CPU-Z/DevCheck 记录 ABI、`/proc/cpuinfo` 硬件、`ro.dalvik.vm.native.bridge` 仍是 `libhoudini.so` —— 这些是 L3 消不掉的。

#### 7. 复测 99，并如实记录

```powershell
& 'D:\leidian\LDPlayer14\adb.exe' shell pm clear com.nd.aqcenter
& 'D:\leidian\LDPlayer14\adb.exe' shell am start -n com.nd.aqcenter/.splash.SplashActivity
& 'D:\leidian\LDPlayer14\adb.exe' logcat -c
& 'D:\leidian\LDPlayer14\adb.exe' logcat -b crash -d
```

预期（基于 L2）：**仍然 `SIGSEGV`，宿主帧仍全在 `libhoudini.so`**。若如此，说明 P1 只完成了「检测层伪装」，阻断点未变；进入 P2/L4，不要重复装模块。

#### 8. 可选：Play Integrity 相关（PIF/Specter）——只在确认 99 校验 Play Integrity 时做

- PIF v19：Kitsune 模块安装 → 重启；用 Play Integrity API Checker 看 verdict。x86_64 模拟器上 `MEETS_STRONG_INTEGRITY` 通常不可得，`DEVICE` 也可能因 Houdini/属性失败；**对 99 大概率无关**。

### 3.3 P2：LDPlayer x86_64 的 L4 实验路径（不在 L3 承诺内）

> 这些是「如果必须留在雷电」才值得投入的方向；全部**未在本机执行**，且每一步都可能 bootloop。执行前必须按 §5 备份 system.vdi。

#### C1. 换翻译层：libndk_translation 0.2.3

- 来源：`waydroid_script/stuff/ndk.py` 下载 [supremegamers/vendor_google_proprietary_ndk_translation-prebuilt](https://github.com/supremegamers/vendor_google_proprietary_ndk_translation-prebuilt)（Android 13，commit `68734c52556d3d7a6db34c603dd9276915c29f2f`），属性 `ro.ndk_translation.version=0.2.3`。
- 需要落地的文件（脚本里的清单）：`bin/arm`、`bin/arm64`、`bin/ndk_translation_program_runner_binfmt_misc*`、`etc/binfmt_misc`、`etc/ld.config.arm{,64}.txt`、`etc/init/ndk_translation.rc`、`lib/arm`、`lib64/arm64`、`lib/libndk*`、`lib64/libndk*`。
- 关键属性：

```
ro.product.cpu.abilist=x86_64,x86,arm64-v8a,armeabi-v7a,armeabi
ro.dalvik.vm.native.bridge=libndk_translation.so
ro.enable.native.bridge.exec=1
ro.vendor.enable.native.bridge.exec=1
ro.vendor.enable.native.bridge.exec64=1
ro.dalvik.vm.isa.arm=x86
ro.dalvik.vm.isa.arm64=x86_64
```

- 风险：libndk 来自 Android 13 / ChromeOS guybrush 固件，LDPlayer 14 是 Android 14；链接器命名空间、init rc、内核 binfmt 都可能不兼容。**先关闭其它实例、备份 `system.vdi` 再做；复制实例不能隔离 `/system`**。
- 判定：能开机 + `getprop ro.dalvik.vm.native.bridge` 为 libndk + 一个简单 ARM64 App 能启动，才算第一步成功；再装 99 看是否还崩。

#### C2. 换更新版 Houdini：11.0.1b_y.38

- 来源：`waydroid_script/stuff/houdini.py` 下载 [supremegamers/vendor_intel_proprietary_houdini](https://github.com/supremegamers/vendor_intel_proprietary_houdini)（Android 13，commit `2f8f088671182e17e67321e098e8411a3972a628`；README 标注 Houdini `11.0.1b_y.38`，来自 WSA）。
- 文件：`bin/arm`、`bin/arm64`、`bin/houdini`、`bin/houdini64`、`etc/binfmt_misc`、`etc/init/houdini.rc`、`lib/arm`、`lib/libhoudini.so`、`lib64/arm64`、`lib64/libhoudini.so`。
- 风险：商业模拟器（蓝叠等）的 Houdini 是定制集成的，社区经验是「不能随便换」；LDPlayer 是否允许同样未知。**新版可能修异常展开，也可能完全不能启动**。
- 判定同 C1：先保证可开机 + ARM64 App 能跑，再测 99。

#### C3. Frida spawn hook（研究/定位，不作为放行交付）

- 版本：[Frida 17.25.2](https://github.com/frida/frida/releases/tag/17.25.2)；x86_64 宿主用 `frida-server-17.25.2-android-x86_64`。
- 思路（对应 L2 符号/字符串）：
  - 在 `libaqcenter.so` 加载后，按 `base + 0x602908`/`0x602898` hook `AntiDebug::anti/anti_inner`，让返回值恒 0；
  - hook `open/openat/read`，对 `/proc/cpuinfo`、`/proc/self/mountinfo`、`/proc/self/maps`、`/dev/qemu_pipe` 返回干净内容；
  - hook `__system_property_get`，把 `ro.dalvik.vm.native.bridge`、`ro.product.cpu.abi*`、`ro.build.fingerprint` 等替换成真机值；
  - 但 NIS 有 `hook_by_tools`/`be_debug`/`lldb_check`/完整性校验；同厂商 `com.nd.myht` 在历史实测中「frida attach 即自杀」。本目标**未测**，很可能注入即退出。
- 结论：Frida 适合做「检测点确认」，不适合当稳定交付；不要把它写进用户操作手册。

#### C4. 宿主/内核层

- 目标：让 guest 内看不到 qemu 设备节点、Intel/hypervisor 标志、Houdini 映射。
- 现实：需要改 LDPlayer 的 VMM/内核或定制 system.img；无公开 turnkey 方案；超出 L3 与本机用户态能力。L2 已把该路径列为「用户态不可达」。

### 5.1 安装 Kitsune / 模块前（必须）

```powershell
$ts = Get-Date -Format 'yyyyMMdd_HHmmss'
Copy-Item 'D:\leidian\LDPlayer14\system.vdi' "D:\leidian\LDPlayer14\system.vdi.bak_l3_$ts"
New-Item -ItemType Directory -Force runs | Out-Null
& 'D:\leidian\LDPlayer14\adb.exe' shell getprop > runs\l3_props_before.txt
```

> 下文以主实例 `--index 1`（adb `emulator-5556`）为例；换实例时把 `--index 1`/`emulator-5556` 换成对应索引与端口，但 `/system` 是共享的，不能靠换实例隔离。

### 5.2 回滚 Kitsune / 模块

1. Kitsune 管理器 → 模块 → 卸载 LSPosed/Vector、Zygisk Next、HMA、PIF；
2. 关闭 Zygisk；
3. Kitsune → 卸载 Magisk（若提供「恢复原厂 /system」）；不成功则走 5.3；
4. 重启，确认 `su -c id` 回到 LDPlayer 自带 root（`/system/xbin/su` 存在）或按需关闭 root。

### 5.3 system.vdi 恢复（bootloop / 改坏 /system 时）

```powershell
& 'D:\leidian\LDPlayer14\ldconsole.exe' quit --index 1
Copy-Item 'D:\leidian\LDPlayer14\system.vdi.bak_l3_<时间戳>' 'D:\leidian\LDPlayer14\system.vdi' -Force
& 'D:\leidian\LDPlayer14\ldconsole.exe' launch --index 1
```

> 注意：`D:\leidian\LDPlayer14\system.vdi.bak_20261103_153004` 是 L1/L2 期间留下的备份；它可能已包含 L1 的属性修改。恢复前先确认备份来源/时间，不要把「L1 前的干净盘」和「L1 后的盘」搞混。

### 5.4 属性回滚

- L1/L2 改过的 `ro.product.*`、`ro.build.fingerprint` 等：按 `runs/l3_props_before.txt` 与原 L1 回滚手册逐项恢复；
- 用 `ldconsole setprop` 写入的属性，重启后仍生效的，按原记录改回；不要用 `resetprop` 写入不会持久化的临时值冒充已回滚。

### 5.5 翻译层替换回滚（P2）

- 恢复原 `libhoudini.so` / `lib/arm` / `lib64/arm64` / `bin/houdini*`；恢复 `ro.dalvik.vm.native.bridge=libhoudini.so`、`ro.enable.native.bridge.exec=1` 等；
- 若已 bootloop，直接按 5.3 恢复 system.vdi。

### 5.6 99 数据

- L2 已备份 `/sdcard/aqcenter_data_backup/` 与本地 `runs/l2/aqcenter_data_backup/`（42,419,903 B）；
- 本方案只做 `pm clear`，不删除用户数据备份；恢复时 `cp -a` 回 `/data/user/0/com.nd.aqcenter` 并修 owner/SELinux（按 L2 回滚手册）。

## 7. 下一步建议（按投入产出排序）

1. **先做 P0**：借/租一台 ARM64 Android 14 真机，按 §3.1 跑 30 分钟；这是唯一能直接判定「99 是否可用」的实验。
2. 若 P0 通过：把「真机型号/系统版本/是否 root/是否装框架」记入 L3 记录，后续同账号在模拟器里不要再试。
3. 若必须留在 LDPlayer：**不要重复 L3 伪装**；直接开 L4 工单，按 §3.3-C1/C2 在关闭其它实例、备份 `system.vdi` 后做翻译层替换实验，或按 §3.3-C3 做 Frida 定位（先确认注入不被杀）。
4. 服务端「环境违法」如果出现在干净 ARM64 真机上：按 §3.1-A 的排除法处理账号/网络/设备风控，不再走模拟器路线。
